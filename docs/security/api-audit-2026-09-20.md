# API security audit — 2026-09-20

Scope: MiniZap API source, replay policy, HTTP handling, SQLite persistence, backup lifecycle, isolated Node runtime, systemd confinement and Caddy routing. Testing used local temporary databases for abuse cases; live checks are limited to normal health/CORS requests and one unlisted replay. This is a targeted review with regression tests, not a claim of a complete penetration test or immunity to attack.

## Findings and remediation

| ID | Severity | Finding | Remediation |
| --- | --- | --- | --- |
| API-01 | High availability risk | Per-request and per-IP limits did not cap cumulative SQLite growth; daily snapshots accumulated indefinitely on the shared VPS disk. | 25,000-record admission cap plus 64 MiB SQLite page limit; new writes fail safely at capacity while existing records remain available. Daily backups verify integrity before rotation and retain seven matching snapshots. Unrelated files/symlinks are never removed. |
| API-02 | Medium integrity risk | A replay could reproduce correctly while specifying wind=999 or equipping a locked talent. The previous validation checked numerical bounds and final simulation results, but not all game input rules. | API derives expected wind from the recorded seed/time and requires each allocated talent's parent rank. Adversarial flights are rejected before simulation/storage; canonical game physics and legacy local replay behavior remain unchanged. |
| API-03 | Medium availability risk | Upload body size/time were bounded individually, but concurrent incomplete uploads had no global admission limit. Verification slots were released before worker termination completed. | At most 32 simultaneous uploads, 128 backend connections and two verification workers. Slots remain occupied until termination completes; each worker has a 64 MiB old-generation limit. Existing per-IP limits and deadlines remain active. |
| API-04 | Medium maintenance risk | API Node 24.18.0 preceded the July security release. | Isolated runtime updated to 24.21.0 using `sec-helper`, exact package version and lockfile integrity; install scripts/cooldown/proxy checks remain enabled. Shared Node runtimes and Caddy are not upgraded. |
| API-05 | Low / defense in depth | Runtime/source archive files retained the workstation UID; the API could initiate connections to localhost admin/co-hosted backend ports if compromised. | Root ownership for MiniZap runtime/releases, private 0700 state directory, empty capability set, additional systemd namespace/kernel restrictions, loopback-only IP access, and denied `connect` syscall. The API accepts proxied inbound requests but performs no outbound requests. |
| API-06 | Low information reflection | JSON parser diagnostics could echo part of a caller's malformed body. | Generic malformed-JSON error; no request body excerpt returned. Proxy address trust also requires a loopback peer and a valid IP address. |

The high severity for API-01 reflects possible exhaustion of the filesystem shared with other applications, not evidence that disk exhaustion occurred. API-04 is security patch lag: the reviewed code does not expose Node's HTTP/2 server, Permission Model, SQLTagStore or DNS resolveAny interfaces covered by the July advisory. No exploit of those runtime CVEs was demonstrated.

## Controls checked

- SQL uses prepared statements; replay IDs are restricted to 12 base64url characters. Names remain data and frontend rendering uses textContent/escaping. No uploaded code is executed; verification executes only the fixed simulator over validated inputs.
- 32 KiB request body limit, JSON-only writes, bounded simulation duration, per-client request/post rates, connection limits and process memory/CPU/task limits.
- Cross-origin allowlist is exact and does not allow credentials. CORS is not authentication; this is intentionally a public submission API, including non-browser clients.
- Caddy sanitizes forwarded headers by default, and only loopback proxy peers are trusted by the application. Backend listener remains 127.0.0.1:3001. HTTPS verification does not disable certificate checks.
- Database and snapshots are outside release/public directories. No frontend or API route exposes filesystem contents, environment files or credentials.
- Core/game simulation files are unchanged. The separate server policy limits which replays may be admitted to persistent/public storage.
- Existing les.bar and Asgard services, routes and shared runtimes are outside the change scope; their process identities and baseline responses are checked around deployment.

## Evidence

- 66 core tests and 12 API integration tests pass on Node 24.21.0 (78 total); full Chromium suite passes.
- Added local regressions cover reproducible invalid wind/builds, storage row/page limits, deduplication at capacity, incomplete upload admission/recovery, timeout recovery, malformed body reflection, spoofed forwarding without trust, chunked overflow, SQL/path payloads and safe JSON headers.
- Snapshot tests verify integrity/content, retention and protection of unrelated files/symlinks.
- Runtime installed/audited through sec-helper; `node-linux-x64@24.21.0` integrity is recorded in `deploy/runtime/package-lock.json`. The staging copy was rejected by the VPS installed-package audit, so activation stopped. A host-local sec-helper install of the exact lockfile then passed audit before activation.
- Security fixes deployed as `security-v1` on Node 24.21.0. All 12 API tests passed on the VPS; a fresh unlisted HTTPS replay exercised the restricted worker/write path. Daily backup succeeded; outbound-connect test returned EPERM. Caddy checksum and other service process IDs/start times and endpoint responses remained unchanged.
- Initial frontend push `7cd008f` completed GitHub Pages workflow [35497102184](https://github.com/expeter/potatoegun/actions/runs/35497102184); live query-based short links return HTTP 200.

## Remaining limitations

- No accounts or authenticated score ownership: names can be impersonated, valid runs can be generated programmatically, seeds can be chosen and rankings can be spammed within quotas. Verification establishes game-rule consistency, not human play. Unlisted links are publicly readable by holders and their contents can be reposted.
- Botnets, IPv6 address rotation and upstream bandwidth exhaustion require edge/network protections beyond this single-process API. Quotas bound storage/resource use but may reject legitimate new submissions during abuse or at capacity. The client retains its full-link fallback.
- Seven local backups bound snapshot growth but do not cover loss of the VPS. Off-VPS copies and capacity/availability alerting remain operational follow-up work.
- The database cap excludes short-lived WAL/SHM files and temporary backup output. Normal checkpoints/read lifetimes and bounded writes limit these in this application; this is not a filesystem quota or protection from an attacker already controlling the service UID.
- The deployed engine rejects incompatible old engine versions; historical replay-engine preservation is a separate product decision.
